TASK: Integrate Sony USB-PTP/OTG into the Existing WED Faces Camera Operator App

You are provided with two source archives:

1. "WED-Faces-Camera-Operator-source-final_2.zip" — the existing main Android app. Extract and work inside its "native-android/" project. This is the application we must preserve and improve.
2. "sony-camera-android-main.zip" — a Sony USB camera-control project and library. Use it as the reference and code source for Sony USB-PTP connectivity, not as a replacement app.

Your task is to implement the complete required Sony USB camera workflow inside the existing WED Faces Camera Operator app.

Do not create a separate app. Do not replace the existing UI or server system. Do not remove existing features. Focus only on Sony cameras. Canon and Nikon are out of scope.

1. Inspect Both Projects First

Read the source code, manifests, Gradle files, existing documentation, tests, API client, camera gateway, ViewModel, Compose UI, transfer queue, foreground services, and workers before making changes.

The existing WED Faces app already contains:

- WED Faces authentication and token refresh.
- Server URL configuration and album selection.
- Camera Wi-Fi PTP/IP connectivity.
- Camera metadata and thumbnail browsing over Wi-Fi.
- Selected-original download, upload queue, progress, retry, import status, and background upload workers.
- Phone-folder watch and a separate Test Mode.

The current main app does not yet have a verified USB/OTG camera transport.

The Sony USB reference project provides a USB Host/PTP connection engine, Sony-specific camera operations, live-view support, and app-initiated photo capture/download. Its README reports testing on the Sony α6600. Other Sony models must be treated as unverified until tested.

Important: Do not assume that the Sony library already supports browsing every card folder or automatically detecting every photo taken with the physical camera shutter. Inspect and implement these missing capabilities.

After the initial inspection, continue with the implementation without asking for permission at each step. Ask only if a genuinely blocking decision cannot be determined from the source or requirements.

3. USB Cable and OTG Connection

Implement a real wired USB-PTP connection using Android's USB Host API and the Sony reference library where appropriate.

Physical connection flow

1. The user connects the Sony camera to the phone with a data-capable USB cable and the correct OTG adapter, or a compatible USB-C-to-USB-C data cable.
2. Check whether the Android phone supports USB Host/OTG. If it does not, display a clear compatibility message.
3. The camera must be powered on and configured for the required USB mode, normally PC Remote or another mode confirmed to work on that camera model.
4. Detect the attached device through "UsbManager" and verify that it exposes a compatible USB/PTP interface and the required endpoints.
5. Show Android's actual USB permission dialog. Never pretend permission was granted.
6. After permission is granted, open the USB device, claim its correct interface, initialize the PTP transport, open the PTP session, perform the Sony-specific initialization, identify the model, and enumerate the available camera storage.
7. Show "Connected" only after the connection and initialization genuinely succeed.
8. Keep the USB session owned by one component. Do not let multiple services or adapters try to open the same USB interface simultaneously.

The phone's USB connection is for camera communication. Server uploads must continue over the phone's normal internet connection, independently of the USB connection.

Connection status and error handling

Display useful connection states:

- No USB camera detected
- USB device detected
- Waiting for permission
- Connecting
- Initializing camera
- Connected / Ready
- Reading memory card
- Downloading original
- Reconnecting
- Connection failed

Show actionable messages for unsupported phones, possible charge-only cables, denied USB permission, incompatible PTP interfaces, camera sleep/off, incorrect USB mode, another application holding the interface, missing card, timeouts, and connection loss.

Disconnect and recovery

The "Disconnect" button must stop camera polling, finish or cancel in-progress work safely, release USB resources, close the session appropriately, and return to the disconnected state.

If the cable is unplugged during a transfer, mark the affected item as retryable or failed. Never mark an incomplete transfer as successful.

Implement safe reconnect behavior where possible. Reinitialize the PTP session after reconnecting and prevent duplicate uploads.

Use an appropriate foreground service and integrate the Sony library's connection lifecycle cleanly. Do not create two independent USB-session owners.

Add a clear way to choose:

- "Camera Wi-Fi"

The common camera workflow must support:

If the database schema needs additional fields, implement a safe migration and preserve existing queue records.

Serialize USB PTP operations through a single session lock. Do not execute simultaneous PTP commands against the same transaction stream.

5. Browse the Entire Accessible Camera Card

The user needs to open the Sony camera's memory card and navigate through its actual folder structure.

This is the camera card, not the phone's Gallery or the existing Phone Folder Watch.

Storage and folders

1. Enumerate available camera storages using PTP storage operations.
2. If more than one storage is exposed, allow the user to choose it.
3. Read folder and file metadata while preserving parent-child relationships. Use appropriate PTP operations such as "GetStorageIDs", "GetObjectHandles", and "GetObjectInfo", or the correct operations supported by the camera.
4. Recognize folder/association objects separately from image files.
5. Display a real folder browser with breadcrumbs, current-folder information, a back/up button, refresh, folders, and image entries.
6. Tapping a folder opens it. Tapping an image opens its preview.
7. Support selecting one image, multiple images, all supported images in the current folder, or a complete folder including descendants where the camera exposes the hierarchy.
8. Show the number of photos selected when selecting a folder. Exclude folders themselves and unsupported files from upload selection.
9. Preserve selection while navigating where possible. Refresh must not silently clear valid selections.
10. Handle multiple storage IDs and avoid collisions in object handles.

Do not flatten the entire memory card and discard the folder hierarchy.

Do not issue delete, rename, format, write, or camera-card modification commands. Browsing is read-only; uploading is a separate read operation.

If the camera does not expose the complete folder hierarchy through its supported PTP mode, report this limitation honestly. Do not fabricate folders or claim complete card access without verification.

Supported image formats

The existing WED Faces backend documents JPG/JPEG, PNG, and WEBP uploads.

Allow selection and upload of formats accepted by the existing server. Other entries may be shown but must be marked unsupported and disabled for upload, with a useful explanation. Examples include Sony RAW/ARW, video, and unknown formats unless the backend contract explicitly supports them.

A failure to read one file's metadata must not prevent other files from appearing.

7. Manual Upload

Provide "Upload Selected (N)" and "Upload Now" in the single-photo preview.

Before starting an upload, verify that the user is signed in and has selected a destination WED Faces album. If either is missing, explain that Settings must be completed first.

For camera photos:

1. Add the selected files to the existing persistent queue.
2. Download the full-resolution originals through the correct active transport.
3. Write each original to the existing app-private transfer staging area.
4. Verify that each download completed before setting the item to upload-ready.
5. Enqueue each completed original immediately into the existing WorkManager upload/import pipeline.
6. Use the existing API, status polling, queue states, retry behavior, and import reconciliation.

Preserve the original image bytes and EXIF metadata. Do not resize, recompress, or replace the original with a preview.

Use bounded-memory or file-based transfer where feasible. Avoid loading multiple large camera originals into "Bitmap" or large in-memory "ByteArray" objects.

Show real per-file states and progress in the existing Queue screen.

A failed file must not block unrelated successful files. If the internet is temporarily unavailable after a successful download, keep the private staged file for retry.

If USB disconnects before the original is retrieved, mark the item as retryable. Prevent duplicate server uploads/imports when retrying.

Never report success until the existing server APIs confirm it.

9. Auto Upload from the Physical Camera Shutter

This is a core requirement. Do not confuse it with taking a picture through an in-app remote shutter button.

The photographer will normally press the physical shutter button on the Sony camera. The app must detect newly created card images and process them according to the Auto Upload setting.

Detection implementation

First inspect the actual Sony USB reference APIs and events.

The reference event "CameraEvent.PhotoCaptured(Bitmap)" alone is not proof that every physical-shutter photo is detected, nor does a bitmap represent the full-resolution original.

Implement a genuine detection strategy using the capabilities supported by the target body:

- Listen for a reliable PTP "ObjectAdded" or equivalent camera event when available.
- Where required, use serialized, bounded polling of object handles, metadata, or Sony's transfer queue.
- Avoid aggressive polling that blocks downloads or overwhelms the camera.
- Verify whether physical-shutter capture detection works on the actual target model.

"Auto Upload" toggle

- Display a clear "Auto Upload" ON/OFF switch.
- Default to OFF unless the user explicitly saved a prior preference.
- Require a ready camera connection, valid sign-in, and a destination album before turning it on.
- If any prerequisite is missing, explain the missing step and do not silently enable it.

When Auto Upload is enabled:

1. Record a baseline of the images that already exist on the card.
2. Detect images positively identified as new after Auto Upload was enabled.
3. Add the new images to the Camera screen and enqueue supported originals automatically.
4. Download each original into private temporary storage, verify completion, and immediately send it through the existing upload/import queue.
5. Show real progress and final import status.
6. Retain retryable errors when connection or upload fails.

Do not upload old card photos automatically just because the camera connected or the Auto Upload switch was enabled. Existing photos are handled through manual selection.

Store a stable identity using the camera identity, storage ID, PTP handle and/or metadata. Repeated events, polling, reconnects, process restarts, or retries must not cause duplicate uploads.

When Auto Upload is OFF, new physical-shutter photos should appear in the Camera screen for manual selection and "Upload Now" / "Save to Phone". They must not be automatically uploaded.

Auto Upload must not save images to public Gallery automatically. Upload and Save are independent actions. Private temporary staging is allowed for transfer reliability.

If the camera does not reliably expose physical-shutter-created images over this USB mode, document it as unverified rather than claiming success.

10. Original Transfer, Memory, and Privacy

- Never convert the original photo to a bitmap and upload that bitmap.
- Never use a live-view frame or thumbnail as the uploaded original.
- Use a file-based transfer approach with bounded memory for large originals where practical.
- Use unique safe filenames and an incomplete/temporary staging process.
- Only mark a file upload-ready after a complete successful download.
- Delete partial files after failed transfers; retain completed staged files for retry; clean temporary files following the existing app's successful-import lifecycle.
- Use cancellation-safe coroutines, timeouts, a single PTP command mutex, and appropriate recovery for stale handles, sleeping camera, card changes, unplugged cables, and failed transfers.
- Keep authentication tokens and secrets in the existing secure store. Do not log passwords, access tokens, authorization headers, or image data.
